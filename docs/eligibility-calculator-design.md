개정 2026-11-08(작업 0·3): 정책대출 숫자를 공식 페이지로 다시 대조해 `docs/policy`에 넣었고(loans.md 8~13절 신설), 규칙 파일 `rules/tables.json`·`rules/loans.json`·`rules/check.mjs`를 만들었다. 독립 검토 반영으로 입력 칸이 바뀌었다 — ① Q1은 「이번 대출로 사는 집·분양받는 집 제외」로 묻는다(분양 당첨자가 분양권 때문에 걸리지 않게) ② Q3 자녀 수는 이미 태어난 자녀만 묻는다(대출 상품은 태아를 세지 않음, `kidsLoan = kidsMinor`) ③ 배우자 소득 칸은 2년 안에 낳은 아이의 다른 부모(혼인신고 전)에게도 묻는다(신생아 특례는 부모 합산) ④ `saleWin`(주택드림·신혼희망타운·그 밖·아님)과 `landLease`(토지임대부 본청약·사전청약·아님)를 나눴다(주택드림 통장으로 토지임대부에 당첨되는 경우) ⑤ 신혼 1인 소득 경로는 부부 모두 소득이 있을 때만 연다(`dual`) ⑥ 곧 분가하는 사람의 가구원 수는 분가 뒤 등본 기준. 13절 C34(특례보금자리론)·C33(더나은보금자리론, 취급 확인 필요 줄 유지)·C47(태아 미포함)·C55(P3 공제 있음·P4 없음)·A1(신생아 최장 20년)·A2(보금자리 11-09 공시)·A12(2023-02-21)·C59(무순위 상세에 민영/국민·규제 칸 없음)는 정리됐다.

## 0. 한 줄 요약

블로그 모든 화면에 떠 있는 **리모컨**(15절)을 누르면, 휴대폰에서 질문 화면 8~10개(한 화면에 질문 1~3개, 2-2)에 답해 브라우저 안에서만 계산한 결과를 본다. 리모컨 안에는 확인기 두 개가 따로 있다. **「정책대출」(1단계)**은 **지금 신규 취급 중인 국가 정책대출 전부(구입 8 · 전세 4 · 월세 2 · 피해·이주 특수 목적 7, 합계 21종)**를, **「특공 자격」(2단계)**은 특별공급 5종을 「공통 요건 충족 / 확인 필요 / 해당 안 됨(입력 기준)」으로 보여 준다. 두 확인기는 질문·결과·계산이 따로이고, 같은 화면 안에서 공통 값(소득·가구 등)을 미리 채워 주는 것만 한다(2-5). 분양 분석 글에서 리모컨을 열면 「보고 있던 ○○단지 정보로 계산할까요?」를 묻고, 예를 누르면 주택형을 골라 분양가·지역·전용면적·민영/국민을 채운다(16절). 대출은 조건 맞는 상품마다 **최대 예상 금액**과 **예상 금리(기본금리~입력으로 확인된 우대 반영)**를 붙인다. 목록은 금리·한도 순이 아니라 고정 분류 순(구입 → 전세 → 월세 → 특수 목적)이라 권유가 아니다. 은행 자체 상품과 시중 금리는 다루지 않는다. 신규 취급이 끝났거나 취급 여부가 확인되지 않은 상품은 별도 줄로 날짜·대체 상품과 함께 보인다. 항목마다 티스토리 신청·조건 글, (특공은) 그 특공 물량이 있는 공고(청약홈·auleezip), 공식 확인처로 잇는다. 리모컨은 스킨 JS가 띄우므로 이미 공개된 글을 다시 저장하지 않는다. 공고 정보는 매일 수집이 이미 받는 응답에서 남기고(API 추가 0건), 2026-12-01 전에 쌓기 시작한다(16-2). 규칙은 커밋되는 JSON(`rules/`)에 한 번만 적고, 숫자마다 `docs/policy/*.md`의 해당 행과 자동으로 대조한다.

## 1. 목표와 범위

### 1-1. 목표

- 블로그 어느 화면에서든 리모컨을 눌러 바로 조회한다(사용자 원문 「티스토리 옆에 리모컨처럼 떠서, 언제든지 눌러서 조회해 볼 수 있는 기능」). 보던 글을 떠나지 않는다(15절).
- 휴대폰에서 2분 안에 결과를 본다. 결과는 먼저 보여 주고, 판정에 더 필요한 질문은 해당 카드 안에서 받는다.
- 결과는 판정이 아니라 **예비 확인**이다. 오판할 바에는 「확인 필요」로 내린다. 다만 사용자가 답하지 않은 것이 없으면 특공 카드에도 「공통 요건 충족」이 나와야 한다(공고마다 다른 조건은 상태를 바꾸지 않고 안내로만 붙인다).
- 정책대출과 특공은 억지로 묶지 않는다. 「내 요건으로 어떤 특공에 넣을 수 있는지」는 특공 확인기가 따로 계산한다(사용자 결정 4).
- 분양 분석 글을 보다가 열면 그 공고 정보를 가지고 들어갈지 묻는다(16절, 사용자 결정 3).
- 사용자가 원한 연결, 즉 "지원 가능한 목록 → 내 블로그 글 → 심화 분석(auleezip)"을 각 확인기 안에 넣는다(대출은 1단계, 특공 물량 공고 목록은 2단계).
- 입력값은 저장하지도 보내지도 않는다.

## 2. 사용자 흐름 (휴대폰 375px 기준)

### 2-1. 원칙

- 리모컨 안의 두 확인기(「정책대출」「특공 자격」)는 질문 화면·답·결과·계산이 모두 따로다(사용자 결정 4). 한 확인기의 답이나 결과는 다른 확인기의 판정에 들어가지 않는다. 같은 뜻의 칸을 미리 채워 보여 주는 것만 한다(2-5).
- 계산기는 계산기 페이지 본문 폭에 그린다. 휴대폰(375px)을 기준으로 한 줄 배치를 만들고 PC에서도 그대로 쓴다(15-2).
- 한 화면에 질문은 1~3개만 둔다. 예/아니오 버튼을 앞에, 숫자 칸을 뒤에 둔다(조사 ux (1)).
- 숫자는 판정 경계가 정해진 곳이면 구간 버튼으로 받는다. 예: 순자산 「3.45억 이하 / 3.45억~5.11억 / 5.11억 넘음 / 모름」. 경계가 정해져 있으니 결과는 숫자를 받을 때와 같고, 휴대폰에서 더 빠르다.
- 모든 질문에 「모름」이 있다. 앞 답 때문에 필요 없어진 질문은 건너뛴다(미혼이면 배우자 소득을 묻지 않는다).
- 질문마다 한 줄 풀이를 단다. 예: "세대주 = 주민등록등본 맨 위에 있는 사람". 긴 도움말은 리모컨 안에서 펼침으로 연다. 리모컨이 이미 시트라서 시트 위에 시트를 겹치지 않는다(15-3). 펼침 모양은 기존 바텀시트(`skin/style.css:364-389`)의 글자·여백 토큰을 쓴다.
- 위쪽에는 진행 표시(3/6)만 둔다. "지금 가능성 있는 항목 N개"는 두지 않는다(개수가 줄어드는 것이 부정적 신호이고 화면을 차지한다).
- 입력 칸은 `<form>`으로 감싸지 않는다. GA4 향상된 측정의 양식 이벤트를 피하기 위해서다(9-4).

### 2-4. 결과 화면 구성

결과는 확인기 탭 안에만 그린다. 두 확인기의 결과를 한 목록·한 요약 줄로 합치지 않는다.

공통(두 탭 모두):

1. 고정 한 줄: 「입력하신 값으로만 본 예비 확인이에요(기준일 2026-10-23). 실제 자격은 입주자모집공고와 기관 심사에서 정해져요.」 기준일은 그 확인기가 쓴 규칙 가운데 가장 오래된 `checked`다.
2. 공고를 가져왔으면 그 아래 「○○단지 84A 공고 정보로 계산했어요 [주택형 바꾸기] [공고 정보 빼기]」 한 줄(16-5).
3. 고정 경고(9-1의 H10 문구). 탭마다 하나씩 둔다.
4. 요약 한 줄: 그 탭의 개수만 센다(예: 「공통 요건 충족 1 · 해당 안 됨 4」).
5. 「해당 안 됨」 카드는 접어서 묶음 맨 아래에 둔다. 펼치면 항목마다 처음 걸린 이유 한 줄이 보인다.
6. 맨 끝: 반영하지 않은 항목 목록과 상세 면책.
7. 「다시 하기」는 그 탭의 답만 지운다(다른 탭의 답과 가져온 공고 정보는 그대로). 리모컨을 닫았다 열면 같은 페이지 안에서는 답이 남고, 페이지를 옮기거나 새로고침하면 모두 사라진다(9-4). 공유는 글 주소만 한다(입력값은 넣지 않는다).

정책대출 탭: 묶음 순서는 구입 → 전세 → 월세 → 특수 목적(Q0에서 고른 것만)으로, 묶음 안 순서는 1-2의 상품 번호 순(P1→P8, J1→J4, M1→M2, S1→S7)으로 고정한다. 금리·한도·상태 순으로 정렬하지 않는다(9-2). 상태가 같지 않아도 번호 순서는 바뀌지 않고, 「해당 안 됨」만 접힌다. 「해당 안 됨」 아래에 「신규 취급 종료」「취급 여부 확인 필요」「출시 예정」 줄을 둔다(1-3).

특공 자격 탭: 카드 순서는 신혼 → 생애최초 → 신생아 → 다자녀 → 노부모 → (기관추천 안내)로 고정한다. 공고를 가져왔으면 카드 위에 「이 공고의 특별공급 세대」 표(16-5)를 둔다.

카드 버튼은 ① 「신청 방법·조건 글」(내 티스토리 글) ② 「이 유형 물량이 있는 공고」(특공만) ③ 「공식 확인」(운영시간을 함께 적는다. 청약홈 청약자격진단은 평일 09:00~17:30, 조사 ux 표). 밖으로 나가는 링크와 내 블로그 글 링크 모두 새 탭으로 연다. 같은 탭으로 옮기면 답을 저장하지 않으므로 리모컨의 답이 사라지기 때문이다.

### 2-5. 공통 값 미리 채우기 (사용자 결정 4)

- 대상 칸: 두 확인기에 같은 문구로 있는 `house`, `marriage`, `kidsMinor`, `newborn`, `age`, `head`, `household`, `incSelf`, `incSpouse`, `everOwned`. 특공에만 있는 칸(`otherAdults`, `incOthers`, `fullYear*`, `rank1`, `won*` 등)과 대출에만 있는 칸(`price`, `deposit`, `loanNow`, `special[]` 등)은 건너가지 않는다.
- 방법: 한 확인기에서 답한 값이 있으면, 다른 확인기를 처음 열 때 Q1~Q6을 한 화면에 모아 「정책대출에서 넣은 값이에요. 맞으면 그대로 쓸게요」 + [맞아요] [고칠게요]로 보인다. 확인 없이 조용히 쓰지 않는다. 고친 값은 그 확인기에만 남고, 먼저 답한 확인기의 값은 바꾸지 않는다(두 쪽 결과가 서로 따라 바뀌지 않게).
- 값은 리모컨 스크립트의 메모리(변수)에만 있다. localStorage·sessionStorage·쿠키·URL에 쓰지 않고 어디로도 보내지 않는다(9-4). 페이지를 옮기면 사라진다.
- 판정은 확인기마다 자기 답 객체로만 한다. 한 확인기의 결과(예: 「신혼 특공 충족」)를 다른 확인기의 입력으로 쓰지 않는다.

## 4. 규칙 데이터 설계 ("DB" = 커밋되는 JSON)

### 4-1. 파일

```
rules/
  tables.json    공통 표(소득표, 수도권 시·도), 공유 조건 defs, presets(글 주소 → 리모컨 탭·유형), boundaryPct
  special.json   특공 프로그램
  loans.json     정책대출 21종(구입·전세·월세·특수 목적)과 종료·확인 필요·예정 상품 줄(offer)
  cases.json     손으로 쓴 대표 사례(경계 사례는 check.mjs가 facts에서 자동 생성)
  check.mjs      로컬 점검(4-5)
  zip_links.json (Q5 승인 시) 공고번호 → {apt, deep, deepAt}
```

- `site/`와 `data/`는 `.gitignore`에 있다. 그래서 원본은 `rules/`에 둔다. `posts/`와 `docs/policy/`는 커밋 대상이라 Actions에서 읽을 수 있다.
- 배포할 때는 파일 여러 개를 `site/rules.json` 하나로 합친다(휴대폰 요청 1회). 리모컨을 처음 열 때만 받는다(15-4).
- 공고 정보 `site/notices.json`은 규칙이 아니라 수집 결과다. `rules/`에 두지 않고 `crawler/fetch.mjs`가 매일 쌓는다(16-2).
- 1단계에는 `special.json`이 없어도 된다. 합치기 단계는 있는 파일만 합치고, calc.js는 `special` 묶음이 없으면 특공 탭을 그리지 않는다.

### 4-2. 스키마 원칙

1. **숫자는 `facts`에 한 번만 적는다.** 조건식, 리모컨 화면 표시, 검색용 정적 설명 글 본문(`posts/calc_post.mjs`, 14절 Q2)이 모두 이 값을 쓴다.
2. **각 fact는 문서의 표 행을 가리킨다.** `doc: {file, section, row}`. 점검은 그 행 안에서만 `text`를 찾는다. 파일 전체 검색은 같은 글자("5.11억")가 여러 상품 행에 있어 아무것도 못 잡는다(실현성 M2, 정확성 M10).
3. **법·주택 구분이 다르면 `variants`로 나눈다.** 특공은 `private`(민영)·`national`(국민), 대출은 상품 안 하위 유형(디딤돌 일반·생애최초·신혼·2자녀). 변형마다 따로 판정해 카드에 줄로 보여 준다.
4. **지역별 값은 `v: {capital, other}`로 둔다.** 엔진이 `capital` 답으로 고른다.
5. **`until`은 필수다.** 정해진 날짜가 없으면 다음 변경이 예상되는 날을 넣고 `untilNote`에 "추정"이라고 적는다. 지나면 그 프로그램은 「확인 필요(기준이 지났어요)」가 된다.
6. **공고마다 다른 조건은 `notice`다.** 상태를 바꾸지 않고 펼침 안에 안내로만 둔다.
7. **`"schema": 1`**. calc.js는 아는 버전이 아니면 확인기를 그리지 않고, 리모컨 안에 「지금은 계산할 수 없어요」와 대표 가이드 글 링크만 보인다.
8. **대출은 `offer`(취급 상태)가 필수다.** `active`(판정) · `ended`(신규 취급 종료) · `unverified`(취급 여부 확인 필요) · `planned`(출시 예정). `active`가 아니면 `when`·`limit`·`rates`를 두지 않고 `offerNote`(날짜와 확인 수준, 예: 「취급은행 공시 기준 2024-12-31 신규 접수분까지, 기금 공식 공지 미확인」)와 `instead`(대체 상품 id 목록)만 둔다.
9. **대출 순서는 `order`(정수) 하나로 정한다.** 1-2의 상품 번호 순서다. 엔진은 이 값으로만 정렬하고, 금리·금액·상태로 정렬하는 코드를 두지 않는다(9-2).
10. **금액과 금리는 선언형이다.** 한도는 `limit.terms`(항 목록)를 `min`으로 합치고, 금리는 `rates`(표 + 가산 + 우대 + 상한 + 하한)로 적는다. 항의 종류와 가산·우대 연산은 calc.js에 고정된 몇 가지만 쓴다(4-4). 일반 수식 문법은 두지 않는다.

### 4-3. 조건식 문법

- 묶음: `all`, `any`, `not`, `{"use": "defs 이름"}`(공유 조건).
- 잎 조건:
  - `{f, is}` — 선택형 답 비교. `is`는 값 하나나 배열.
  - `{f, op, fact | v | tbl}` — `op`는 `le`·`lt`·`ge`·`gt`. 공식 문구("이하", "초과")와 1:1로 맞춘다. 표 참조는 `{"tbl": "urban_sale_2025", "pct": 130, "by": "household"}`.
  - `{notice}` — 상태를 바꾸지 않는 안내.
  - `{unknownIf: "사유"}` — 그 경로에 도달하면 「확인 필요」(예외 경로: 1주택 대환, 처분 조건, 8인 초과).
- 모든 잎에 `why`(거짓일 때 보일 한 줄)를 단다. `ask`는 모름일 때 카드 안에 띄울 2차 질문 칸 이름이다.
- 잎의 `skipIf`(조건식)가 참이면 그 잎을 참으로 본다. 원문 단서 「…신청자는 소득 초과 시에도 대출 신청 가능」처럼 요건을 면제하는 경우에만 쓴다(토지임대부, 4-4). 잎에 붙인 `unknownIf: {조건, why}`는 그 조건이 참일 때 그 잎을 모름으로, `notice: {when, text}`는 조건이 참일 때만 안내를 붙인다. 변형의 `keyIf`는 조건이 참이면 facts를 다른 변형 키로 고른다(예: solo30 → solo30First).
- 입력 칸은 2-2·2-3 표의 이름만 쓴다. 파생 칸은 calc.js에 고정한다: `incCouple = incSelf + incSpouse`, `incHousehold = incCouple + incOthers`, `incMonth = incHousehold × 10000 ÷ 12`(원), `incSelfMonth`, `incSpouseMonth`, `incOne = min(incSelf, incSpouse)`(신혼 1인 경로), `incDti`(1인 경로면 `incOne`, 아니면 `incCouple`), `soloHead = (marriage=미혼 ∧ head=세대주 ∧ household=1)`, `dual = (incSelf>0 ∧ incSpouse>0)`, `capital = (region ≠ 그 밖 지역)`, `area60·area85·area100`(면적 구간에서), `kidsLoan`(대출 자녀 수, 지금은 `kidsMinor`와 같음 — 태아·성년 자녀 포함 여부 미확인, 13절 C47). check.mjs는 이 두 목록에 없는 `f`를 거절한다.

### 4-5. 갱신과 검수 (`rules/check.mjs`, 로컬 관문)

1. **필수 칸**: `id, name, when, links.guide, links.official, checked, until, refresh`. 모르는 `op`·`f`는 실패.
2. **숫자 대조**: `fact.text`를 만원으로 바꾼 값이 `fact.v`와 같고, `doc`이 가리키는 표 행 안에 `text`가 있어야 한다. 소득표 값도 쉼표 형식("7,533,763")으로 해당 행에 있어야 한다.
3. **확인일**: `checked`는 참조한 문서 행들의 「확인일」 칸 가운데 가장 이른 날과 같아야 한다. `refresh_guides.mjs`가 규칙의 `checked`를 함께 올리는 방식은 쓰지 않는다. 일부만 다시 본 문서 때문에 확인하지 않은 날짜가 붙기 때문이다(정확성 M11).
4. **링크**: `guide`가 `posts/published.json` 값에 있어야 한다. 예약 글은 `published.json`에도 이미 들어가므로(`tistory/draft.mjs:31-37`) 이것만으로는 부족하다. 그래서 배포 합치기 단계가 `posts/scheduled.json`에서 같은 주소의 공개 시각을 찾아 `guideAfter`로 넣고, calc.js는 그 전까지 `fallback`(허브 글)을 보여 준다. 손으로 옮겨 적지 않는다.
5. **사례**: `cases.json`의 손 사례와, facts에서 자동으로 만든 경계 사례(`v`, `v+1`, 모름)를 모두 돌린다.
6. **기한**: `until`이 지났으면 실패, 30일 안이면 경고. `checked` 경과(monthly 35일, semimonthly 20일, yearly 400일)는 경고만 낸다.
7. **금지 표현**: `posts/check.mjs:8`의 `BANNED`(내보내지고 있다)를 가져와 `why`·`name`·`notice`·라벨을 검사한다. 고정 용어 허용 목록(`기관추천`)은 빼고 검사한다. 계산기 전용 추가 목록은 「대출 가능」「승인」「당첨 가능」「자격 있음」「대상입니다」「통과」「유리」「가장 낮은」「꼭 신청」「추천」「최저 금리」「더 많이」「신청하기」이다(9-2).
8. **money.mjs 대조**(3단계 전까지 임시): `posts/money.mjs:16-37`의 겹치는 상수(디딤돌·신생아·보금자리 한도·소득, 순자산, 3.31억, 7,533,763원)가 facts와 같은지 본다.
9. **바뀐 값 안내**: 숫자를 바꾼 규칙에는 `changed: {date, text}`를 붙인다. 카드에 「연결 글은 ○월 기준이에요. 바뀐 값: …」 한 줄이 나오고, 14일이 지나도 남아 있으면 경고한다. 그동안 해당 가이드 글을 `data/guide_refresh.txt` 맨 앞에 넣는다(정확성 M12).
10. **대출 금액·금리 칸**: `offer`가 `active`면 `limit.terms`와 `rates`가 있어야 하고, `rates.rows` 각 행의 칸 수가 `cols` 수와 같아야 한다. 금리표 값은 문서 표 행에 그대로 있어야 한다(2번과 같은 행 단위 대조). `active`가 아니면 `offerNote`와 `checked`가 있어야 한다.
11. **순서**: `order`가 묶음 안에서 겹치지 않아야 한다. calc.js와 `calc_post.mjs`에 `rates`·`limit` 값으로 정렬하는 코드가 있으면 실패시킨다(문자열 검사 `sort(`가 `order` 말고 다른 칸을 쓰는지).
12. **DTI 검산**: calc.js의 `pmt` 역산이 `posts/money.mjs`의 `principalOf`와 같은 값을 내는지 대표 3건(예: 디딤돌 소득 2,000만원·30년 3.10% → 약 2억 3,418만원, 5,000만원·30년 3.80% → 약 5억 3,652만원, 3절 신생아 → 약 10억 905만원)으로 본다. calc.js는 의존성 없이 같은 식을 한 줄로 둔다.

숫자를 바꾸는 순서: 공식 출처 확인 → `docs/policy/*.md` 수정 → 사용자 승인 → `facts` 수정과 `changed` 표시 → `node rules/check.mjs` → push → 재배포(6-3).

### 5-1. 위치

- `skin/images/calc.js` 한 파일에 순수 함수 `match(group, answers, today)`, 리모컨 껍데기(15절), 공고 가져오기(16절), 두 확인기 화면을 둔다. `calendar.js:69`의 return과 섞이지 않게 따로 둔다.
- **확인기 분리(사용자 결정 4)**: `match`는 묶음 하나(`rules.loans` 또는 `rules.special`)와 그 확인기의 답 객체 하나만 받는다. 정책대출 화면은 `match(rules.loans, loanAnswers)`, 특공 화면은 `match(rules.special, specialAnswers)`만 부른다. 3값 논리·조건식 해석 같은 부품은 같은 코드를 쓰지만, 답 객체·결과·요약 개수는 섞지 않는다. 미리 채우기(2-5)는 화면 단계에서 값을 복사할 뿐 `match`는 다른 확인기의 답을 모른다.
- 파일 머리는 `(function (g) { g.CY = { match }; if (typeof document === 'undefined') return; … })(this)` 모양으로 둔다. node 점검은 `node:vm`으로 읽어 `CY.match`만 꺼낸다(실현성 L1). 빌드 도구·의존성은 없다.
- 규칙 주소는 `window.CHEONGYAK_SCHEDULE_URL`의 폴더에서 `rules.json`을 구한다(`skin/skin.html:266`). 스킨 옵션을 새로 만들지 않는다(`apply_skin.mjs:11-12`는 index.xml을 다루지 않는다).
- 받는 것은 GET뿐이고, 계산은 모두 브라우저에서 한다. `rules.json`은 리모컨을 처음 열 때, `notices.json`은 분석 글이거나 `#n=`일 때(16-1), `schedule.json`은 특공 「물량이 있는 공고」 목록을 펼칠 때(2단계)만 받는다. 리모컨을 열지 않는 방문자는 calc.js 한 파일만 받는다(15-4).

### 5-2. 판정 규칙

- **3값**: 참 / 거짓 / 모름. `all`은 거짓 하나면 거짓, 아니면 모름 하나면 모름. `any`는 참 하나면 참, 아니면 모름 하나면 모름.
- **모르는 예/아니오 칸이 3개 이하**면 가능한 값을 모두 넣어 평가한다. 결과가 모두 같으면 그 값을 쓴다. 예: 맞벌이 여부를 몰라도 어느 쪽이든 참이면 참이다(실현성 L2). 4개 이상이면 모름으로 둔다.
- **상태**:
  - 거짓 → **해당 안 됨(입력 기준)**. 처음 걸린 잎의 `why`를 쓴다. `softFail` 잎(규제지역 5년 제한)은 거짓이어도 「확인 필요」로 둔다. 비규제지역 공고는 신청할 수 있기 때문이다.
  - 모름, `unknownIf`, 경계값, `until` 경과, 범위 밖 변형 → **확인 필요**. 이유와 `ask` 질문을 카드에 띄운다.
  - 참 → **공통 요건 충족(입력 기준)**. `notice`는 펼침 안에 둔다.
- **변형·구간**: 특공은 변형(민영·국민)마다 `tiers`를 순서대로 평가해 처음 참인 구간을 붙인다. 모든 구간이 모름이면 「소득 구간 확인 필요」다. 대출은 맞는 변형마다 카드 안에 한 줄씩 최대 예상 금액·예상 금리를 보인다(줄 순서는 `variants` 순서, 금액 순이 아니다). 맞는 변형이 없고 모름인 변형이 있으면 「확인 필요」다.
- **소득 정확도(정확성 H1·H2)**:
  - 특공 소득은 `incHousehold`(성년 가구원 전원)를 쓴다. 대출은 `incCouple`을 쓴다.
  - `fullYear*`가 아니오인 사람이 있으면 특공 소득 구간은 「확인 필요: 실제 산식은 작년 총급여 ÷ 근무 개월 수예요」로 둔다.
  - 질문 문구의 "작년"은 날짜로 바꾼다. 공고일이 4월 1일(사업자 7월 1일) 전이면 전전년도 서류를 쓴다는 안내를 붙인다(`special.md:166-167`).
  - 노부모 특공은 피부양 부모 소득도 넣는다(`special.md:108`). 그래서 노부모를 고르면 `otherAdults`·`incOthers`를 필수로 한다.
- **경계값**: `|입력 − 기준| ≤ boundaryPct%`이면 기준의 어느 쪽이든 「확인 필요(기준값 근처)」로 둔다. 특공 월소득과 대출 연소득 모두에 적용한다(정확성 M5, L3).
- **단위**: 입력은 만원 정수(`inputmode="numeric"`), 표는 원이다. 표에 공식 금액이 있으면 그 값을 쓰고, 6~8인 비율 금액처럼 계산해야 하는 값은 계산 후 「확인 필요」로 둔다.
- **기간**: 날짜는 받지 않고 선택형으로 받는다(입력이 적고 경계 계산 오류가 없다). 기준일이 다른 것(특공 = 공고일, 대출 = 접수일)은 `notice`로 알린다.
- **안전한 실패**: 모르는 `op`나 `f`는 모름이다. 참이 되는 일은 없다. 규칙 읽기에 실패하거나 `schema`가 다르면 확인기를 그리지 않는다(4-2의 7). 공고 정보 읽기에 실패하면 묻지 않고 빈 확인기로 연다.

### 5-3. 최대 예상 금액·예상 금리 계산 (대출)

계산 순서(조사 rent §2의 순서를 이 설계 이름으로 옮긴 것):

1. **취급 상태**: `offer`가 `active`가 아니면 판정하지 않고 묶음 끝 줄(종료·확인 필요·예정)로 보낸다. `instead` 상품 이름을 링크로 붙인다.
2. **기한**: `until`이 지났으면 「확인 필요(기준이 지났어요)」, 금액·금리는 보이지 않는다.
3. **자격**: `when`을 5-2대로 평가한다. 관문 순서는 무주택(P8은 1주택 처분 조건 경로) → 세대주 유형 → 지금 쓰는 대출(종류별, 2-2 `loanNow`. 모르면 확인 필요. 기존 대출이 필요한 대환 상품에는 걸지 않음) → 공공임대 입주 → 생애 1회(M1) → 상품 고유 요건 → 소득(부부합산, 신혼 1인 경로) → 순자산 → 주택(면적·집값·보증금·월세 상한, 지역)이다. 「해당 안 됨」이면 금액·금리를 계산하지 않는다.
4. **변형별 금액**: 맞는(또는 모름인) 변형마다 `limit.terms`를 계산해 `min`을 낸다.
   - 입력이 없는 항(집값 모름 등)은 빼고 계산한 뒤 「상품 한도 기준 최대」라고 적는다.
   - `pick` 조건이나 공제 금액이 모름·범위면 가능한 값마다 계산해 「a~b원」으로 보인다(예: 규제지역 모름, 경기·인천 소액임차보증금 2,500만~4,800만원).
   - 금액은 만원 미만을 버리고 「약 n억 n,nnn만원」으로 적는다. 정해진 항(상품 한도·보증금 × 비율)은 「약」을 붙이지 않는다.
   - 어느 항에서 정해졌는지 한 줄(「← 상품 한도에서 정해짐」)을 붙이고, 모든 항은 「계산 보기」 펼침에 둔다.
5. **DTI 항(구입만)**: `L_DTI = (DTI% × 연소득 − otherInterest) ÷ (12 × pmt(1, 기본금리, term))`.
   - 가정: 원리금균등, 거치 없음, 만기 `term`(기본 30년), 계산 금리는 그 소득·만기 칸의 기본금리(우대·가산 전), 소득은 부부합산(신혼 1인 경로는 그 1인, `incDti`).
   - 신생아 특례(P2)는 특례 기간(기본 5년)이 끝나면 금리가 오르지만(지금 표로 +0.75%p, 계산값) DTI는 만기 내내 특례금리로 계산한다. 화면 가정에 「특례 기간 금리로 계산」을 적는다. 대부분 상품 한도에서 금액이 정해져 결과는 바뀌지 않는다(검증 formula 15, FP05030801·FP05030808).
   - 기금 DTI의 정확한 정의(다른 대출을 이자만 넣는지)는 미확인이다(13절 C24). `otherInterest` 기본값 0이면 「다른 대출 이자를 0원으로 계산했어요」를 붙인다.
   - 전세·월세에는 DTI 항이 없다(기금 전세 페이지에 DTI 조건이 없고, 전세대출은 DSR 적용 제외 — 금융위 2025-10-15, https://www.fsc.go.kr/no010101/85432). 보증기관의 소득 기반 한도(HUG ③, HF 상환능력별)는 계산하지 않고 안내로 둔다.
6. **예상 금리**:
   - 기본 = 표[소득 구간][만기 또는 보증금 구간]. 소득이 구간 경계 ±`boundaryPct`% 안이면 양쪽 행을 모두 보인다(상태는 바꾸지 않는다).
   - 가산(`adjust`)을 더한다: 지방 −0.2%p(원문에 문구가 있는 상품만. S1 FP05070001·S2 FP05021201·S3 050510001·S4 050560001에는 없으므로 넣지 않는다), 신혼 1인 기준·토지임대부 `maxRowPlus`, 보금자리 규제지역 +0.2%p(전세사기피해자 제외). 방식 가산(고정·변동)은 사용자가 방식을 고르지 않으므로 더하지 않고, 원문에 문구가 있는 P1(FP05030101)·P3(FP05030601)·P4(FP05030901)만 펼침에 적는다.
   - 우대는 **입력으로 확인되는 것만** 뺀다: `one` 묶음은 가장 큰 것 하나, `add` 묶음은 합. 합은 `prefCap`까지, 결과는 `floor` 밑으로 내려가지 않는다.
   - 화면: 「예상 금리 연 a%~b%」(a = 우대 반영, b = 기본 + 가산). 확인된 우대가 없으면 한 값만 쓴다. 입력으로 보지 않은 우대(`prefOther`)는 빼지 않고 이름만 펼침에 둔다.
   - 금리는 소수 둘째 자리까지 원문 그대로 쓴다(반올림하지 않는다).
7. **고정 문구**(카드마다): 「은행·기금 심사(담보평가·신용·보증 한도·선순위 채권)로 달라질 수 있는 예상값이에요」. 구입 묶음 머리에는 「만기 n년·원리금균등·거치 없음으로 계산했어요」. 「대출 가능」「승인」 같은 말은 쓰지 않는다(4-5의 7).
8. **DSR**: 계산하지 않는다. 정책모기지·전세대출은 DSR 미산출로 안내돼 있고(금융위 카드뉴스 2024-08-22, 조사 rent C9), 감독규정 원문은 미확인이다(13절 C23). 묶음 경고 아래에 「DSR 등 은행 심사는 반영하지 않았어요」를 둔다.

## 6. 티스토리 삽입(리모컨)과 배포

원안의 「본체 글 2편 안 자리 div 계산기 + 가이드 글 5편 끝 작은 계산기(embeds)」는 쓰지 않는다. 계산은 모두 리모컨(15절) 안에서 하고, 글에는 리모컨을 여는 길만 둔다(사용자 결정 2).

### 6-1. 넣는 곳

| 곳 | 방식 | 단계 |
|---|---|---|
| 모든 화면(홈·글·카테고리 목록·청약일정) | 오른쪽 아래 리모컨 버튼(15-1). calc.js가 그리는 링크 하나다. 글 HTML에는 아무것도 넣지 않는다. 탭 바는 3칸 그대로 | 1 |
| 계산기 페이지(일반 글 1편) | 본문은 설명·기준표(`posts/calc_post.mjs`), 계산기는 calc.js가 주소로 알아보고 그린다(15-2) | 1 |
| 분양 분석 글(티스토리) | **글을 다시 저장하지 않는다.** 카테고리와 본문 청약홈 링크로 판정해 리모컨 버튼 주소에 `#n=`을 붙인다(16-1) | 1 |
| 대표 가이드 글·「대출·정책」 카테고리 글 | **글을 다시 저장하지 않는다.** `presets`(4-4)로 리모컨을 그 유형으로 열고, calc.js가 본문 끝에 「내 조건으로 정책대출 예비 확인 →」 한 줄(누르면 리모컨이 열림)을 붙인다. 가이드 51편을 저장 대기열에 넣지 않는다(`DAY_MAX = 3`, `tistory/draft.mjs:20`, 대기 15편 `data/guide_refresh.txt`) | 1(「청약가이드」·특공은 2) |

- 리모컨 틀은 `skin.html`에 HTML로 쓰지 않고 calc.js가 그린다. 글 페이지마다 같은 빈 틀이 반복되면 색인에 불리했던 2026-10-26 교훈(`CLAUDE.md` 변경 이력, 홈·달력 틀을 `<script type="text/template">`로 감싼 일)과 같은 이유다. HTML에 더하는 것은 탭 바 칸 하나와 `<script>` 한 줄뿐이다.
- 해시 `#calc=`·`#n=`은 calc.js만 읽는다. calendar.js는 청약일정 화면에서 `#week`만 본다(`calendar.js:58`). 해시에는 입력값을 넣지 않는다(9-4).
- 티스토리 앱·RSS에서는 스킨 JS가 돌지 않는다고 추정한다. 리모컨은 없고, 정적 글의 기준표와 글 링크가 그대로 보인다. `#calc=` 링크 문구는 「블로그에서 열면 내 조건으로 확인할 수 있어요」로 둔다.

**검색용 정적 설명 글을 남길지 — 권장: 남긴다(확인기마다 1편, 14절 Q2)**

- JS가 그린 리모컨 내용과 결과는 색인되지 않는다. 리모컨만 두면 「정책대출 자격 확인」「특별공급 소득 기준 계산」 같은 검색으로 들어올 문서가 블로그에 없다(8-1).
- 21종 기준을 한 표로 모은 글은 상품별 가이드(/11·/15·/22 등)와 겹치지 않는다. 상품별 자세한 조건은 가이드 글이, 한눈에 보는 기준표와 「내 조건으로 확인」 입구는 이 글이 맡는다.
- `calc_post.mjs`가 rules에서 만들어 숫자 사본이 생기지 않고, 기존 저장·예약·갱신 흐름(하루 3편 안 1편)을 그대로 쓴다. 자리 div가 없으니 원안의 「div가 저장 후 남는지」 실측도 필요 없다.
- 반대 근거: 「정책대출 계산기」「특공 자격 계산기」는 자동완성이 없었다(조사 ux (6)). 유입 기대가 크지 않으므로 리모컨 공개를 이 글에 묶지 않고 리모컨 공개 뒤 따로 낸다(10절 작업 9). 내지 않기로 하면 `calc_post.mjs`를 만들지 않는다.
- 일반 글로 두는 이유: 숫자 주소(/NN)는 제목을 바꿔도 그대로이고, RSS·카테고리·`published.json`·예약·갱신 흐름을 그대로 쓴다. 티스토리 「페이지」는 주소가 제목 글자로 만들어진다(바닥글 소개 페이지 주소, `skin/skin.html:256`). 제목을 바꾸면 주소가 바뀌는지는 미확인이다.

### 6-2. 만들기 전 실측 (작업 1)

1. 이미 공개된 분양 분석 글 1편과 청약일정 주간 글 1편의 렌더 HTML을 **읽기만** 해서 `.post-body` 안 `a[href*="applyhome.co.kr"][href*="houseManageNo="]`가 그대로 남는지, `.post-cat` 링크가 `/category/분양분석`인지 확인한다(16-1). 초안 대조(`tistory/draft.mjs` compare)는 글자만 비교하므로 이것만으로는 판단하지 않는다. 원안의 「비공개 시험 글 저장」은 자리 div가 없어져 하지 않는다.
2. (정적 글을 낼 때) 그 글을 비공개 저장한 뒤 렌더 HTML에 `#calc=` 링크가 남는지 본다. `TISTORY_DUMP`와 `--dry-run`은 편집기 안 상태만 보여 줘서(`tistory/draft.mjs:3,61`) 이것만으로는 판단하지 않는다(실현성 H4).
3. Detail 응답의 `HOUSE_DTL_SECD_NM`(민영/국민), `PUBLIC_HOUSE_SPCLW_APPLC_AT`(공공주택특별법), 규제 표시(`SPECLT_RDN_EARTH_AT` 등)와 주택형 응답의 특공 유형별 세대수 칸은 `posts/analysis_post.mjs:32,100,128-139`가 쓰고 있고 저장 원본 `data/notice_text/2026000496.models.json`(로컬)에서 확인했다. fetch 경로(APT·무순위) 응답에서도 같은 칸인지는 작업 2 첫 Actions 실행 때 이미 받는 상세·주택형 행의 키 목록을 로그로 한 번 찍어 확인한다(추가 호출 0건, 16-8). `crawler/check.mjs`는 API 키 없이 가짜 행으로 매핑만 점검하므로 실제 응답 확인에는 쓸 수 없고, 새 칸 매핑(`types[]`·`houseKind`·`publicLaw`·`regFlags`)의 가짜 행 점검만 거기에 더한다.
4. 휴대폰 「모바일웹 자동 연결」이 꺼져 있는지 본다(`README.md:9`).
5. 애드센스 앵커·자동 광고가 켜져 있는지 사용자가 관리 화면에서 확인하고(14절 Q13), 실제 휴대폰에서 탭 바·리모컨 시트와 겹치는지 본다(15-5).

### 6-3. 배포

- `daily.yml` build 단계에서 upload 전에 합치기 단계를 넣는다(`daily.yml`은 지금 fetch 다음 곧바로 upload).
  - `rules/*.json`과 `posts/scheduled.json`을 읽어 `site/rules.json` 하나로 쓴다(`guideAfter` 채우기 포함).
  - JSON 파싱과 최소 스키마(필수 칸, `schema`)를 검사한다. 실패하면 job을 실패시키지 않고 지금 배포본의 `rules.json`을 받아 쓴다. `crawler/fetch.mjs:151` `PREV_URL` 방식과 같다. 매일 받는 `schedule.json` 배포는 막히지 않는다(실현성 M9).
- 규칙만 고쳤을 때 바로 반영하려면 `on.push.paths: [rules/**]`를 더한다. push 이벤트에서는 fetch 대신 지금 배포본 `schedule.json`을 내려받아 쓴다(배포 주소 `posts/weekly.mjs:8`). **API 추가 호출 0건**이다. 사용자 결정 Q5.
- 공고 정보 `site/notices.json`은 `crawler/fetch.mjs`가 같은 실행 안에서 `site/`에 쓴다. `daily.yml`은 지금도 fetch 다음 `site/`를 통째로 올리므로(`daily.yml:24-31`) 단계를 더하지 않는다. 쌓기·대체본·지우기는 16-2. push 이벤트(규칙만 고친 경우)에는 지금 배포본 `notices.json`을 내려받아 그대로 쓴다.
- `rules/check.mjs` 전체는 Actions에서 돌리지 않고 로컬 관문으로 쓴다.
- 스킨: `tistory/apply_skin.mjs --apply --file images/calc.js`를 하고, **skin.html도 함께** 적용한다. calc.js를 고칠 때마다 캐시 주석을 고쳐야 `_version_`이 바뀐다(`skin/skin.html:267`).

### 7-2. 특공 결과 → 그 유형 물량이 있는 공고 (2단계)

- 「공통 요건 충족」이나 「확인 필요」인 특공 유형마다 다음을 모두 만족하는 공고를 특공 접수일 순으로 최대 5개 보여 준다. 조건: 접수가 끝나지 않음(`zip/post.mjs:73` `closedOf`와 같은 판정), `spUnits[유형] > 0`, `houseKind`가 그 줄의 판정 변형(민영/국민)과 같음, `publicLaw`가 아님.
- `houseKind`·`publicLaw`를 모르면 「주택 구분 확인 필요」 표시와 함께 보여 준다.
- 공고일이 2026-06-15 이전이면 「종전 규정」 표시를 붙이고, 민영 신생아는 2026-06-15 이후 공고만 보여 준다(`special.md:191`, 정확성 M13).
- 목록 제목은 「이 유형 특별공급 물량이 있는 공고(자격은 공고문 확인)」로 고정한다. "내가 넣을 수 있는 단지"로 읽히지 않게 하기 위해서다.
- 줄마다 연결 순서는 auleezip 심층(`deep-{키}`, 열려 있을 때만) → 시세비교(`apt-{번호}`) → 청약홈 `applyhomeUrl`이다. 기존 규칙(`zip/post.mjs:193-197`, `zip/pages.mjs:29`)과 같다. `zip_links.json`이 없는 동안(Q5 전)에는 청약홈 주소와 auleezip 첫 화면(`/`)만 쓴다. `data/zip_posts/index.json`과 `data/zip_deep/*.json`은 gitignore라 Actions에서 읽을 수 없다.
- 한계: 특공 세대수는 APT 공고에만 있다(무순위는 특공이 없다, 16-8). 오피스텔·도시형 API에는 특공 구분이 없다(조사 wordpress (3)). 거주 시·도는 묻지 않으니 전국 공고가 섞인다. 「해당지역 / 기타지역」 표시는 3단계에서 거주 시·도 질문과 함께 넣는다.
- 공고를 가져온 상태(16절)면 목록 맨 위에 그 공고를 고정하지 않는다. 그 공고의 세대수는 이미 카드 위 표(16-5)에 있고, 목록은 「다른 공고」 찾기용이다.

### 7-3. auleezip·분석 글 → 리모컨 (1단계, 16절)

- 원안의 「2단계 `#n=` 링크로 특공 유형 미리 고르기」는 16절로 옮겨 1단계에 넣는다. 티스토리 분석 글은 링크 없이 본문에서 공고번호를 읽고(16-1), auleezip 심층 글은 끝 링크 `#n=공고번호`로 연다(16-7). 공고번호는 개인정보가 아니다.
- 정책대출 탭은 그 공고의 주택형으로 분양가·면적·지역 등을 채우고, 특공 탭(2단계)은 결과 맨 위에 「이 공고의 특별공급 세대: 신혼 N · 생애최초 N」을 보여 준다(사용자·유입 M5).

### 7-4. API

- 새 외부 호출은 없다. 특공 세대수, 주택형별 분양가·면적, Detail 칸은 이미 부르는 응답에서 남긴다(16-2). 지난 배포본 `notices.json`을 받는 것은 배포 주소라 API가 아니다(`crawler/fetch.mjs:12,151`과 같은 방식).
- 기금 금리 공개 엔드포인트(`NewBabyGetInform.jsp`)는 이용약관이 미확인이라 정기 호출하지 않는다. 금리는 사람이 확인해 문서에 넣은 값만 쓴다. 나중에 쓰려면 `zip/guard.mjs`에 한도를 먼저 등록한다(메모리 「API 호출 한도 가드」).

## 8. 측정과 유입

### 8-1. 검색

- JS가 그린 리모컨과 결과는 색인되지 않는다. 검색용은 정적 설명 글(6-1, 14절 Q2)의 본문(설명, 기준표, 질의응답 문단)이다. `calc_post.mjs`가 rules에서 만들어 숫자가 어긋나지 않는다. 리모컨 틀을 HTML에 쓰지 않는 것은 「빈 틀 반복」 문제의 교훈과 같다(`CLAUDE.md` 변경 이력 2026-10-26).
- 리모컨 자체의 유입 효과는 검색이 아니라 이미 들어온 방문자(분석 글·가이드 글 독자)의 다음 행동이다. 그래서 8-3의 판단 기준도 리모컨 열기 비율을 본다.
- 검색은 "[유형] 자격 확인 / 소득 기준 계산" 꼴로 들어온다. 「정책대출 계산기」·「특공 자격 계산기」는 자동완성이 없었다(조사 ux (6), 2026-11-05).
- 제목 제안:
  - 「특별공급 자격 확인·소득 기준 계산(2026년) — 신혼부부·생애최초·신생아」
  - 「정책대출 자격 확인(2026년) — 디딤돌·신생아 특례·보금자리론·버팀목 조건 계산」
  - 숫자 주소라 연도를 바꿔도 링크는 그대로다. 연도 표기 갱신은 기존 월간 갱신 흐름을 탄다.
- 유형별 검색("신혼부부 특별공급 소득 기준 계산")은 기존 대표 글(/26 등)이 더 잘 맞는다(추정). 그래서 그 글들에서 리모컨을 열면 유형이 미리 골라지게 한다(`presets`, 6-1).

### 8-2. GA4 이벤트

- `calc_open{tab: loan|special, from: button|tabbar|inline|hash}`, `calc_done{tab}`, `calc_out{link_type: guide|notice|official}`, `calc_notice{answer: yes|no}`만 보낸다. `calc_notice`에 공고번호는 넣지 않는다(어느 단지를 보는지는 page_view로 이미 알 수 있고, 계산 이벤트와 묶으면 개인의 관심 단지와 계산 여부가 이어진다).
- `calc_step`은 보내지 않는다. 건너뛴 화면 번호로 미혼·무자녀를 짐작할 수 있기 때문이다(정확성 M9, 실현성 L8).
- 입력값, 결과 개수, 상품 id는 보내지 않는다. 상품 id로 출산·혼인을 짐작할 수 있다.
- 네이버 애널리틱스에는 맞춤 이벤트를 보내지 않는다.

### 8-3. 판단 기준 (설계값, 사용자가 바꿀 수 있다)

- 1단계(정책대출) 공개 4주 뒤 `calc_done / calc_open` 30% 이상, `calc_out / calc_done` 20% 이상인지 본다. 2단계(특공)는 사용자 결정 순서대로 진행하되, 미달이면 특공 탭을 더하기 전에 질문 수와 결과 화면을 먼저 고친다. 분석 글에서 `calc_notice` 예 비율이 낮으면 묻는 문구를 고친다. 30%·20%는 사실이 아니라 출발점으로 정한 값이다.
- 리모컨이 모든 화면에 있으므로 「page_view 대비 `calc_open`」도 본다. 기준값은 두지 않고(근거 없음) 첫 4주 값을 출발점으로 삼는다.

## 9. 정확성·법적·개인정보 안전장치

### 9-1. 문구

- 결과 맨 위(2-4의 1): 기준일과 「예비 확인」.
- 정책대출 탭 위(구입 묶음): 「집 계약 전에 기금e든든(또는 HF)에서 사전 자산심사·대출 가능 여부를 먼저 받으세요. 이 화면 결과로 계약하지 마세요.」(정확성 H10)
- 특공 자격 탭 위(2단계): 「부적격 당첨이면 당첨이 취소되고 일정 기간 청약이 제한될 수 있어요. 신청 전 청약홈 청약자격확인(평일 09:00~17:30)에서 확인하세요.」 제한 기간 숫자는 공고문이나 규칙에서 확인한 뒤에만 쓴다(13절 C19).
- 페이지 끝: 반영하지 않은 항목(부양가족, 무주택 예외, 과거 이력의 세부, 은행 심사, 공고별 조건), 그리고 「신청 단계에서는 자격을 검증하지 않고 당첨 뒤 서류를 확인합니다. 부적격 책임은 신청자에게 있습니다」(조사 ux (4)).
- 다자녀 카드에는 「당첨자는 배점 순으로 정해져요」를 늘 붙인다(`special.md:69-80`).
- 금액은 늘 「최대 예상 금액」, 금리는 늘 「예상 금리」 라벨을 쓴다. 금리 옆에 어느 칸의 기본금리인지(소득 구간·만기 또는 보증금 구간)를 적고, 펼침 안에 하한(예: 신생아 디딤돌 1.2%)과, 원문에 문구가 있는 상품(P1·P3·P4)에만 방식 가산(5년 변동 +0.1%p · 10년 고정 +0.2%p · 순수고정 +0.3%p)을 적는다(정확성 M7, 5-3).
- 대출 묶음 머리마다 「상품은 정해진 순서(구입 → 전세 → 월세)로 보여요. 금리·금액 순이 아니에요」를 둔다(9-2).

### 9-2. 금융상품 광고·중개로 읽힐 위험

- **설계 원칙(사용자 결정 2026-11-05)**: 결과는 「조건에 맞는 정책대출 목록」이다. 고정 분류 순(1-2 상품 번호 순서)으로만 보이고, 좋은 순서가 아니므로 권유로 보이지 않는다. 사용자 원문: 「이는 좋은 순서가 아니라 리스트이므로 권유라고 보여질 수 없음」.
- 이 원칙을 지키는 장치(유지):
  - 정렬: 금리·한도·상태 순으로 정렬하지 않는다. 엔진은 `order`로만 줄을 세우고 check.mjs가 다른 정렬을 막는다(4-5의 11).
  - 비교 문구 금지: 「가장 낮은」「유리한」「추천」「더 많이」 같은 상품 간 비교·평가 말을 쓰지 않는다. 「최저 금리 상품」 같은 요약 줄, 상품 간 금액 차이 표시도 두지 않는다.
  - 대상: 국가 지원 정책대출(기금·HF 정책모기지)만 보인다. 은행 자체 상품, 시중 금리, 은행 재원 대출을 섞지 않는다(1-3).
  - 링크: 은행 상품 페이지나 제휴 링크로 보내지 않고 기금·HF 공식 안내와 내 블로그 글로만 잇는다. 기금 계산마법사가 「아니오」 답에 은행 자체 상품 바로가기를 붙이는 것과 달리(조사 rent §3), 이 계산기는 그런 링크를 두지 않는다.
  - 신청 유도 금지: 「신청하기」「지금 받기」 버튼을 두지 않는다. 공식 안내 버튼은 「공식 확인」이다.
- **금융소비자보호법 확인**: 판매업자가 아닌 사람의 광고 제한·미등록 중개 해당 여부는 조문 확인 없이 **사용자 판단으로 진행**한다(2026-11-05). 위 표현 원칙으로 대응하고, 공개 전 별도 법률 확인 단계는 두지 않는다.
- 공고 가져오기(16절)는 그 단지를 권하는 것이 아니다. 묻는 문구는 「보고 있던 ○○단지 공고 정보로 계산할까요?」로 고정하고, 「이 단지 대출 가능」「이 단지에 넣을 수 있어요」 같은 말은 쓰지 않는다. 주택형 목록은 공고 순서이고 가격·한도 순으로 정렬하지 않는다. 특공 탭의 공고 세대 표는 공고의 사실(세대수)만 보인다.
- 대출 결과 옆에 대출 광고가 붙는 문제는 사용자 결정 Q6이다(애드센스 설정 변경). 리모컨은 모든 화면에 뜨므로 원안처럼 「계산기 글 2편」만 골라 막을 수 없다.

### 9-3. 투자 권유 금지(절대 규칙)

- 라벨은 「공통 요건 충족 / 확인 필요 / 해당 안 됨」에 늘 「(입력 기준)」을 붙인다. 「가능」을 단독으로 쓰지 않는다.
- 금지 표현은 check.mjs가 막는다(4-5의 7).

### 9-4. 개인정보

- 입력값은 저장도 전송도 하지 않는다. localStorage·sessionStorage·쿠키도 쓰지 않는다. URL·해시에 입력값을 넣지 않는다(공고번호 해시 `#n=`와 탭 해시 `#calc=`는 입력값이 아니다).
- 리모컨의 답은 calc.js 메모리에만 있고 페이지를 옮기면 사라진다. 공통 값 미리 채우기(2-5)와 공고 정보 채우기(16-5)도 같은 메모리 안에서만 일어난다. 그래서 「이 계산기 코드는 입력값을 저장하거나 보내지 않습니다」 문구를 그대로 쓸 수 있다.
- 공고 정보 파일(`notices.json`)은 공개된 공고 사실만 담는다. 받을 때 아무 값도 함께 보내지 않는다(쿼리 문자열 없음).
- 같은 페이지에서 gtag(`skin/skin.html:10`), 네이버 wcslog(`skin/skin.html:270-271`), 애드센스·티스토리 통계가 돈다. 이 스크립트들이 입력값을 읽는지는 확인하지 못했다(추정). 그래서 문구는 「이 계산기 코드는 입력값을 저장하거나 보내지 않습니다」로 좁힌다(정확성 M9).
- `<form>`을 쓰지 않는다. GA4 향상된 측정의 양식 상호작용 설정이 켜져 있는지는 사용자가 GA 관리 화면에서 확인한다.
- 수집하지 않으면 개인정보처리방침을 고칠 필요가 없는지는 법적 판단 미확인이다.

## 11. 위험과 대응

| 위험 | 대응 |
|---|---|
| 규칙이 틀려 사용자가 부적격 당첨되거나 계약금을 잃음 | 숫자는 문서 표 행과 자동 대조한다. 질문을 세대 소득·민영/국민·세대주·기존 대출·5년 당첨까지 받는다. 경계값·예외 경로는 「확인 필요」로 둔다. 묶음별 행동 경고 문구를 둔다 |
| 특공 카드가 모두 「확인 필요」가 되어 쓸모없어짐 | 공고별 조건은 `notice`로만 둔다. 「확인 필요」는 미답·경계·예외일 때만 나온다. 3절 예시 입력에 「공통 요건 충족」이 나오는지 cases로 고정한다 |
| 질문이 많아 이탈 | 1차 질문 화면은 확인기마다 8~10개(2-2), 나머지는 카드 안 2차 질문. 구간 버튼. 진행 표시. 판단 기준(8-3) |

## 14. 사용자 결정 질문

답변 2026-11-05(사용자 원문은 따옴표 안). 아래가 다른 절보다 우선한다.

1. **단계 순서 — 결정됨**: 「대출 먼저 진행하고 특공 진행」. 1단계 = 리모컨 + 정책대출, 2단계 = 특공 자격 5종, 3단계 = 공공분양 특공.
2. **검색용 설명 글 — 계산기 페이지가 겸한다**: 리모컨 버튼이 계산기 페이지(일반 글 1편)를 여는 방식으로 바뀌어, 그 페이지 본문의 기준표·설명이 검색 입구가 된다(15-2). 따로 내지 않는다.
3. **기준 근처 값 — 질문에서 뺌, 지원금 묶음 추가**: 「기준 근처값이라는게 아니라 청년월세지원과 같은 복지로 나오는 … 을 말하라고」.
   - ±3% 안 「확인 필요」는 사용자에게 묻지 않고 설계값으로 둔다(4-4 `boundaryPct`).
   - 「지원금」 묶음을 정책대출 확인기에 더한다(월세 묶음 다음). W1 청년월세 지원: 만 19~34세, 부모와 따로 사는 무주택 청년, 청년가구 기준 중위소득 60% 이하·자산 1억 2,200만원 이하, 원가구 중위소득 100% 이하·자산 4억 7,000만원 이하, 월 최대 20만원 최장 24개월(생애 1회). 2026년 신규 신청은 3.30~5.29였다(복지로 WLF00004661, 국토부 보도 2026-03-18). 금리가 아니라 지원금이라 금액 칸에 「월 최대 20만원」, 금리 칸에 「금리 없음(지원금)」. 지금 신청 가능한지는 「신청 기간 확인 필요」로 둔다. 숫자는 `docs/policy/`에 행을 먼저 더한 뒤 rules에 쓴다(13절에 C 항목으로 추가할 것: 소득 산정 방식, 24개월 대 12개월 보도 차이).
   - 같은 복지로 주거 지원인 주거급여(임차급여)도 후보. 넣을지는 다음에 묻는다.
4. **대출 금리 표시 — 결정됨, Q9 답변으로 바뀜**: 상품 목록 + 최대 예상 금액 + 금리. 금리는 Q9대로 정책 금리 범위만.
5. **배포 자동화 — 결정됨**: 「배포」. `rules/` push 때 바로 재배포, `zip_links.json` 바뀔 때만 자동 커밋, 둘 다 한다.
6. **애드센스 대출 광고 — 결정됨, 막지 않는다**: 「나도 먹고살아야지 막지마」. 9-2의 광고 결합 위험은 사용자가 감수하는 것으로 기록한다.
7. **HF 보증 + 은행 재원 대출 — 넣는다(별도 묶음)**: 「금리 낮고 한도 높으면 넣어주면 좋은데 한 번 더 확인해봐야지」. 다시 확인한 결과(2026-11-05):
   - HF 특례전세자금보증 무주택 청년: 만 39세 이하 무주택, 부부 합산 연소득 7,000만원 이하(신혼가구는 본인), 보증 최대 2억원(신혼·미성년 자녀 가구 3억원). 다자녀(미성년 2명 이상) 최대 2억원. 목돈 안드는 전세Ⅱ: 보증금 3억원(지방 2억원) 이하, 합산 연소득 6,000만원 이하, 최대 3억원(https://www.hf.go.kr/ko/sub02/sub02_01_04.do, `docs/policy/loans3.md:223-224`).
   - 금리: HF 페이지에 없다. 은행이 자율로 정한다. 블로그·비교 글은 연 3.5~4.5% 안팎(2026년)이라 쓰지만 공식 숫자가 아니다. 정책대출(버팀목 2%대)보다 **금리는 높고**, 대신 **소득 기준이 넓고(5천 → 7천) 한도가 크다(최대 3억)**.

9. **금리 — 정책 금리 범위만**: 「그냥 정책의 금리 범위만 보여주고 자세한건 블로그 글 조회 유도」. 상품마다 공식 금리 범위(예: 디딤돌 연 2.85~4.15%, 신생아 특례 1.8~4.5%, `docs/policy/loans.md:150`) 한 줄과 「신청 방법 글 →」. 소득 구간·우대 반영 계산(5-3 금리 부분)은 하지 않는다. 금액 계산은 그대로.
10. **특공 탭 — 숨김(권장 유지)**: 답 없음. 2단계 전까지 숨긴다.
11. **리모컨 모양 — 결정됨**: 시안 5개(`docs/remote-designs.html`)를 본 뒤 「리모컨 버튼을 누르면 계산기가 들어있는 페이지를 여는 방식」, 「우측 아래 리모컨 버튼식이 좋은 듯」. 오른쪽 아래 글자 버튼(PC·휴대폰 모두) → 같은 탭에서 계산기 페이지(15절). 옆 패널·시트·탭 바 4번째 칸은 쓰지 않는다. 페이지는 1편에 탭 둘(정책대출·특공)로 두었다(따로 2편을 원하면 바꾼다).
12. **auleezip `#n=` 링크 — 뺀다**: 「공고링크 번호는 굳이? 왜 넣으려는건데」. 넣으려던 이유: 워드프레스는 글 안 스크립트를 막아 auleezip에 리모컨을 못 띄우니, 심층 글 끝 링크로 티스토리 리모컨을 그 공고 정보로 열게 하려 했다. 꼭 필요하지 않고 auleezip 독자를 티스토리로 보내는 일이라 1단계에서 뺀다. 6-1·15-2 ④·16-7은 쓰지 않는다. 티스토리 분석 글에서 공고 정보 가져오기(16절)는 그대로다.
13. **애드센스 자동 광고 — 켜져 있음(사용자 기억)**: 「아마 켜뒀을걸 티스토리는 켰던기억 있음」. 리모컨 버튼·시트가 아래 앵커 광고와 겹칠 수 있다. 6-2 실측에서 실제 휴대폰·PC 화면으로 광고 자리를 먼저 보고 버튼 위치를 정한다(광고를 CSS로 가리지 않는다).
14. **분석 글에서 묻기 — 묻는 이유 설명, 한 번만 묻기 유지(이제 계산기 페이지에서 묻는다, 16-3)**: 「분석글에서 공고정보를 왜 물어봐」. 이유: 분석 글은 공고 하나를 다루는 글이라, 그 글에서 리모컨을 열면 그 단지 분양가·지역·면적을 직접 칠 필요 없이 채울 수 있다(사용자 결정 3 「보고 있던 공고 정보를 함께 가지고 들어갈지 물어보는 기능」). 다른 글에는 공고가 없어 묻지 않는다. 묻지 않고 바로 채우는 방식을 원하면 바꾼다. 묻는다면 같은 페이지에서 한 번만.

## 15. 리모컨 버튼 + 계산기 페이지 (1단계)

### 15-2. 계산기 페이지

- **티스토리 일반 글 1편**(14절 Q2의 검색용 설명 글을 겸한다). 숫자 주소(/NN)라 제목을 바꿔도 주소가 그대로다(6-1). 2단계에도 같은 글 하나에 탭 둘(「정책대출」「특공 자격」)을 둔다. 탭은 `#calc=loan`·`#calc=special`로 고른다.
- 본문(글자, 색인됨): 무엇을 해 주는지 두세 줄, 상품별 조건·정책 금리 범위 표(rules에서 생성), 자주 묻는 것, 면책. `posts/calc_post.mjs`가 rules에서 만들어 숫자 사본이 없다. 저장은 기존 `tistory/draft.mjs`(비공개·예약), 공개는 사람이 한다.
- 계산기 화면은 본문에 넣지 않는다. 편집기가 글 안 `<script>`나 빈 div를 지울 수 있기 때문이다. calc.js가 주소(`location.pathname`이 `rules.json`의 `calcPage`와 같을 때)로 이 글을 알아보고 **제목 바로 아래**(`.post-body` 앞)에 계산기를 그린다. 그래서 계산기를 고쳐도 글은 다시 저장하지 않는다.
- 계산기 안(위에서 아래): (2단계) 탭 줄 → 공고 줄(16-5, 있을 때만) → 질문(2절) → 결과(2-4). 결과의 「신청 방법 글 →」은 같은 탭에서 그 글로 간다.
- 질문·결과는 한 페이지 안에서 아래로 이어진다. 시트·모달은 쓰지 않는다. 도움말·「계산 보기」는 펼침(2-1).
- 탭: 탭마다 자기 답·결과를 따로 가진다. 탭을 바꿔도 다른 탭의 답은 같은 페이지 안에서 남는다(2-5). 특공 탭은 2단계 전까지 그리지 않는다(`rules.json`에 `special`이 없으면 탭 줄 없음).
- 처음 고르는 탭·유형: `#calc=` → `#n=`(정책대출 구입) → 기본(정책대출, 유형 미선택).
- 티스토리 앱·RSS에서는 스킨 JS가 돌지 않는다고 추정한다. 그때는 본문 표와 「블로그에서 열면 내 조건으로 확인할 수 있어요」 한 줄만 보인다.

### 15-3. 무게

- 계산기 페이지가 아닌 화면은 calc.js의 버튼 부분만 실행한다(rules·notices를 받지 않는다). 분석 글에서는 본문 청약홈 링크의 번호만 읽어 버튼 주소에 붙인다(파일을 받지 않음).
- 계산기 페이지에서만 `rules.json`을, `#n=`이 있을 때만 `notices.json`을 받는다.
- calc.js 전체를 try로 감싸 오류가 calendar.js나 페이지를 막지 않게 한다(11절).

### 15-4. 접근성

- 계산기 질문은 `<button>`·`<input type="radio">`로 받고 `<form>`은 쓰지 않는다(2-1, 9-4). 누르는 크기 44px 이상.
- 상태는 글자(「공통 요건 충족(입력 기준)」 등)로 쓰고 색만으로 가르지 않는다. 요약 한 줄은 `aria-live="polite"`.
- 탭 줄(2단계)은 `role="tablist"`와 좌우 화살표.

### 16-3. 묻는 문구

- 계산기 페이지가 `#n=`으로 열리면(분석 글에서 리모컨 버튼을 누른 경우) 질문 앞에 한 화면을 둔다.
  - 「보고 있던 「{name}」 공고 정보로 계산할까요?」
  - 「분양가·지역·전용면적·주택 종류를 채워 드려요. 언제든 고칠 수 있어요.」
  - [예, 채워 주세요] [아니요, 직접 입력할게요]
- 페이지를 열 때 한 번만 묻고, 답은 저장하지 않는다(14절 Q14). 「아니요」 뒤에도 계산기 위쪽에 「「{name}」 공고 정보로 채우기」 한 줄을 남겨 마음을 바꿀 수 있게 한다.
- 2단계: 공고는 한 번만 고르고 두 탭이 같은 공고를 쓴다. 특공 탭에서 처음 열었으면 문구는 「보고 있던 「{name}」 공고로 특공 자격을 볼까요?」.
- 쓰지 않는 말: 「이 단지 대출 가능」「이 단지에 넣을 수 있어요」「추천」(9-2).

### 16-4. 주택형 고르기

- 「예」 다음 화면에 주택형을 한 줄씩 보인다: 타입(`ty`에서 앞 0을 뺀 「84A」) · 전용 n㎡(소수 둘째 자리) · 최고 분양가 · 일반 n · 특별 n세대. 공고 응답 순서 그대로이고 가격 순으로 정렬하지 않는다(9-2).
- 주택형이 하나면 고른 채로 보이고 바로 다음으로 간다.
- 「아직 못 정했어요」를 두어, 고르지 않으면 주택형 없이 지역·주택 종류·규제만 채우고 집값·면적은 직접 입력하게 한다.
- 고른 뒤에도 공고 줄의 [주택형 바꾸기]로 다시 고른다. 바꾸면 공고에서 채운 칸만 다시 채우고, 사용자가 고친 칸은 그대로 둔다.

- 채운 칸에는 「공고」 표시를 붙이고 모두 고칠 수 있다. [공고 정보 빼기]는 공고에서 채운 칸만 비운다.
- 소득·가구·무주택 같은 사람 칸은 공고에서 채우지 않는다.

### 16-6. 공고 없는 글

- 가이드 글·주간 글·홈·목록·청약일정에서는 묻지 않는다. `presets`가 있으면 그 유형으로, 없으면 빈 확인기로 연다.
- 분석 글인데 번호가 `notices.json`에 없거나 받기에 실패하면 묻지 않는다. 틀린 값을 채우느니 빈 칸으로 둔다.

### 16-7. auleezip 링크 — 하지 않음

14절 Q12 답변으로 뺐다. 나중에 넣는다면 심층 글 끝에 계산기 페이지 주소 + `#n=번호` 링크 한 줄이면 된다(스크립트 없음).
